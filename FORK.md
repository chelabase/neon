# Chelabase Fork of Neon

This is Chelabase's hard fork of [neondatabase/neon](https://github.com/neondatabase/neon), based on upstream commit fa504217 (2026-08-31, main HEAD when upstream froze). PostgreSQL sources are pulled from [chelabase/postgres](https://github.com/chelabase/postgres) branches `REL_14_STABLE_chelabase` through `REL_17_STABLE_chelabase`.

## Policy

This is a hard fork: all of the code, the core engine included (pageserver, safekeepers, the PostgreSQL patches), is ours to change, and we change it whenever that is the right fix. Where code came from, how invasive a change is, or how far it moves us from the original base is never a reason to leave a bug or document a gap instead of fixing it. Performance changes need supporting profiling evidence.

## Pageserver changes

The changes we made to the pageserver, each fixing a bug Chelabase hit.

- **Detach waits for its ancestors' WAL.** Before copying anything, `detach_ancestor` waits for every ancestor level to ingest its WAL up to the cut (an ancestor reloaded since its last flush only has its WAL up to its disk consistent LSN until its walreceiver catches up). Each wait is up to 30 s, one level after the other, so the worst case is 30 s × the chain's depth; a timeout returns 503 ("not caught up yet, retry later"), a broken ancestor 500.
- **Multi-level detach copies every ancestor's layers.** Under `DetachBehavior::MultiLevelAndNoReparent` the detached timeline gets each level's layers up to that level's cut (straddling deltas rewritten, the rest copied by reference). Before copying, it waits for every level's queued uploads to finish, so a layer copied by reference is already in remote storage (a stopped upload queue answers 503, shutting down). This holds because every layer-map update (flush, compaction and its image layers, gc-compaction, import) schedules its uploads under the same layer-map write lock that makes the new layers visible. Like the HTTP handler's own drain, the wait has no timeout: a stuck upload queue holds the detach until shutdown. Nothing is reparented.
- **Multixact next offset, as Postgres writes it.** A multixact `CREATE_ID` also sets the next multixact's offset (when still zero), as Postgres' `RecordNewMultiXact` does, through one combined record `NeonWalRecord::MultixactOffsetCreateWithNext` at **enum index 8** (just before the testing-only `Test` variant; byte tests pin the indices). `MultixactOffsetCreate` stays decodable but is no longer emitted. This is a stored format: **never roll the pageserver back to a build without the variant** once it has ingested a `CREATE_ID`: its layers then hold discriminator 8, and an older pageserver can't read those pages.
- **Missing multixact offsets pages.** When the next multixact's entry is on the next offsets page (once per 2048 multixacts), ingest checks that the page exists and, if not (WAL from older minors), writes it as one image with the entry set. Mid's own page is never checked: two reads per `CREATE_ID` made multixact ingest about 20× slower. A `CREATE_ID` on an offsets page the pageserver never received (WAL from a compute older than Postgres' 2025-12-03 multixact back-patch, e.g. a physical import from an older minor) fails with "no base image"; Chelabase doesn't run such computes. Revisit before adding physical imports or running computes we didn't build.
- **Reads at retained LSNs below the GC cutoff.** An LSN below a timeline's applied GC cutoff is still served when GC keeps it whole: a child's branch point (`retain_lsns`) or a lease. The match is exact: the LSN equals the kept point, or normalizes (`normalize_lsn`) to the same LSN and lies at or after it. Never below it and no ranges: gc-compaction keeps only the image at the exact point and drops the history below. The same rule applies at every scope check: basebackup (libpq and gRPC), get_page and the other page requests, and branch creation. A branch created there gets its GC cutoff capped at its own branch point, so its computes can read from the start.
- **Leases at kept points.** Every lease is keyed at the exact requested LSN, never normalized (a normalized key let a static compute at a WAL page start lose its point once the cutoff passed it). A read matches a lease when its LSN is equal to the kept point, or the same point past the page header. A lease below the GC cutoff is granted only when the requested LSN is equal to a kept point, or the same point past the page header, checked and inserted under one `gc_info` write lock. Branch creation at a kept point below the cutoff takes a short lease there under that same lock, so a child dropped meanwhile can't let GC (legacy `gc_timeline` or gc-compaction) drop the point before the new branch registers its own. A static compute at a kept point therefore keeps its data through compute_ctl's lease renewal even if the child is deleted. Accepted risk: a reader holding no lease (its lease request failed or was never made) loses the point when the last child that kept it is deleted. On a root timeline its reads then fail; on a branch's parent a page whose history is gone falls through to the grandparent and returns stale data silently (legacy GC works from a snapshot of the retain points taken before the new cutoff is applied). Reads at a point kept by an offloaded child may hit cold layers (performance only).

## Compute extension changes

- **DDL forwarding sends LOGIN, VALID UNTIL and "touched" roles.** `pgxn/neon/neon_ddl_handler.c` adds optional keys to each forwarded role `set` entry: `"login": true|false` (the catalog's value at commit; always sent for a role created in the transaction, otherwise when LOGIN or NOLOGIN was given), `"valid_until": "<text as written>"`, and `"touched": true` when another attribute (CREATEDB, CREATEROLE, INHERIT, REPLICATION, BYPASSRLS, SUPERUSER, CONNECTION LIMIT) or a membership changed: GRANT/REVOKE of a role marks every grantee and granted role, CREATE ROLE ... IN ROLE/ROLE/ADMIN and ALTER GROUP the named role. A touched-only entry is `{"op":"set","name":…,"touched":true}`. A role without a password is sent with an explicit `"password": null` when it was created in the transaction, renamed, or carries any of these keys; attribute-only entries carry no password key; password-only bodies are unchanged (`ALTER ROLE a PASSWORD NULL` alone is still `{"op":"set","name":"a"}`). Savepoints: what a released one gave wins, `touched` is OR-ed, and an entry that gave no PASSWORD clause keeps the parent's password. A rolled-back one counts for nothing, at any depth: a savepoint released into an enclosing one that is then rolled back is dropped with it (its options merge into a table made at the enclosing level, which the rollback drops, and their strings live in memory freed only with that level). compute_ctl's migrations forward like any other session (their GRANTs to the privileged role arrive as touched entries).
- **DDL forwarding tracks roles and databases by OID, never by name.** Keyed by name, with renames chained through `old_name`, a transaction that dropped a role, renamed another onto its name, created a third under it or renamed that one away mixed the roles' state: DROPs were lost, a role created in the transaction claimed an `old_name` (the receiver then moved the old role's row and data keys to it), a dropped role's attributes went out for another role, the payload depended on hash order (database renames and swaps in savepoints too), and some valid transactions failed in the handler itself ("Failed to get encrypted password": a password set before a rename-then-drop was looked up under the dropped name). Now each role a statement touches is recorded by OID with its name before the transaction (the name at its first touch; any rename is a touch) or as created in the transaction (recorded after CREATE ROLE runs, when the OID exists); the options only the statements know (the password as typed, which options were given) are kept per savepoint by OID. At commit the catalog, looked up by OID, says which roles exist and under which names, so savepoint rollbacks need no undo. The payload then follows:
  - a role created in the transaction that exists at commit: a `set` under its name, never with `old_name`, with its password (or an explicit null) and its login;
  - a role from before the transaction that exists at commit: a `set` with `old_name` (its name before the transaction) when renamed, plus whatever its statements changed;
  - a role from before the transaction that is gone: `{"op":"del","name":<its name before the transaction>}`, unless a role now holds that name (a new role, sent with `recreated`, or a rename onto it, which the receiver refuses or replaces when it moves its rows). A role renamed and then dropped is a `del` under its old name, without `old_name`.
  - **Recreated:** a role created in the transaction under a name that held a role, from before the transaction, that is gone (dropped under any name) carries `"recreated": true`, always with `"touched": true` (the old role's members lost their membership). The key is a boolean, sent only when true and only on `set` entries. A name freed only by a rename isn't marked. The receiver runs its DROP-time live data-key check for a recreated entry, so `DROP ROLE app; CREATE USER app [PASSWORD 'x']` can't pass the old role's data keys to the new one. A rename onto a gone role's name is `touched` too.
  - The receiver applies renames, then sets, then dels.
  - **Databases** work the same way: each database a statement touches (CREATE after it runs, ALTER ... RENAME, ALTER ... OWNER, DROP) is recorded by OID with its name before the transaction; at commit a created one is a `set` with its owner, one from before the transaction a `set` with `old_name` when renamed and `owner` (the catalog's) when its owner changed, and a gone one a `del` under its name before the transaction. The receiver keeps a database's owner by name, so every database owned by a role renamed in the transaction is sent again with its owner.
- **PREPARE TRANSACTION is refused while a transaction has role or database changes to forward** ("cannot PREPARE a transaction that changed roles or databases"): the prepared transaction would commit later, maybe in another session, where nothing forwards its changes. Without changes (or with `neon.forward_ddl` off) PREPARE works as before.
- **The DDL forwarding model test.** `test_runner/regress/test_ddl_forwarding_model.py` runs every sequence of role operations (CREATE USER ... PASSWORD, CREATE ROLE, DROP, RENAME, ALTER ... PASSWORD / PASSWORD NULL / NOLOGIN), database renames and savepoints (SAVEPOINT, RELEASE, ROLLBACK TO, nested three deep) up to 5 statements, over three role names (two exist, one backing a live data key) and three database names (two exist, one owned by a role), in five configurations: roles with a short alphabet (38,453 sequences), all role operations (398,382), roles with database renames (111,257, about a third of them rejected by Postgres because the owner of a database can't be dropped), the branch owner and a reserved name (30,313), and the role cap (30,313). Each payload is applied to a model of the receiver (`ddl.rs` `steps()`, `decide()`, `apply()`, `finish_role_moves()`, `finish_db_moves()`, with its owner, reserved-name, live-key and role-cap refusals), and the result must match the catalog after the commit: refusals exactly when the commit broke one of the receiver's rules; copies (verifier and login flag) for exactly the roles with a password; every live data key under its own role's current name; every forwarded plain password the one its verifier was made from; the databases with their owners' current names; `recreated` exactly where a new role took a gone role's name; and a resync asked for when a role from before the transaction was dropped. Two receiver gaps it found are checked against a model with the receiver fixed (and logged against the current one): a branch owner dropped and created again is accepted, and the role cap is checked before the delta's dels (DROP a; CREATE USER c at the cap is refused). It runs in 40 shards, in parallel, and isn't rerun on failure.

## PostgreSQL Minors

When a new PostgreSQL minor release becomes available:

1. Merge the `postgres/postgres REL_x_y` tag into `REL_x_STABLE_chelabase` in chelabase/postgres (pull request, run `make check`).
2. Bump the submodule commit here and update `vendor/revisions.json` (pull request). The gate is `.github/scripts/ci-local.sh` (lint, build, Rust tests) on the bump, plus a local `make check` for that major in chelabase/postgres.
3. Publish dev images with `.github/scripts/publish-dev.sh` and run chelabase's e2e against them.
4. Process oldest minors first.

Neon's own `REL_x_STABLE_neon` branches remain read-only references; we do not track them.

## Tests

CI quarantines known test failures in `test_runner/known_failures.txt`, each with a reason. This list may only shrink.

## Checks

The gate for every PR is `.github/scripts/ci-local.sh`: lint (self-tests, actionlint, fmt, clippy, cargo deny, ruff, mypy), build, and the Rust tests. It runs on a developer machine inside the same `ghcr.io/chelabase/neon-build-tools` image as `.github/workflows/pr.yml` (pulling the image needs no login: the GHCR packages are public), with caches in the Docker volumes `chela-neon-cargo` and `chela-neon-target` and logs under `.ci-local/` (git-ignored). Use `--pg v14|v15|v16` for the older majors.

GitHub CI is manual-only, as standing policy: `pr.yml` is `workflow_dispatch` only, and branch protection on `main` requires a PR but no status check. `images.yml` runs only for `v*` tags and the platform images, by hand.

Neon's pytest regression suite is opt-in and required for no PR: `ci-local.sh --regress [-k <expr>] [-n <workers>]` runs it for a targeted check, for example to debug one test. When an image changes, chelabase's own e2e covers the parts we use. The regression run deselects `test_runner/known_failures.txt` (fails on GitHub's runners too) and `test_runner/known_failures.local.txt` (fails only in the local run); both use the `<nodeid>  # <reason>` format and may only shrink.

Quick mode, for patch work: `ci-local.sh --only build,rust-tests,regress` runs just the listed steps (in pipeline order, lint skipped; the last `--only` decides, and `regress` in it implies `--regress`), and `--test-filter <nextest expr>` (needs `rust-tests` in `--only`) narrows `cargo nextest run` with `-E`, ANDed with the quarantine filter (no newlines; a filtered run skips `cargo test --doc`, which `-E` can't narrow). `CHELA_NEON_VOLUME_SUFFIX=<suffix>` (`^[a-z0-9-]+$`) switches to the volumes `chela-neon-cargo-<suffix>` and `chela-neon-target-<suffix>`, so parallel clones keep separate build state and stamps.

## Publishing dev images

The Postgres 17 dev images are built on a developer machine and pushed from there (the GitHub job took 111 minutes): `.github/scripts/publish-dev.sh [--no-push] [--only storage|compute]` builds `ghcr.io/chelabase/neon-storage:<sha12>-dev` and `ghcr.io/chelabase/neon-compute-v17:<sha12>-dev` from the checked-out commit (`<sha12>` = chelabase's `neon_tag`), runs `image_variant_test.sh` on the storage image, and only then pushes. It needs a clean tree at a commit on `origin/main`, initialised submodules, and `docker login ghcr.io` for the push (the packages are public: pulling needs no login, pushing does), and it refuses to overwrite an existing tag without `--force-retag`. The images carry no SBOM or provenance attestations. To build once and push later, build with `--no-push --allow-unpushed` from the round branch and test those images; once `main` is fast-forwarded to that SHA, `publish-dev.sh --push-only` pushes the exact local images without rebuilding or re-running the variant test. It keeps the push pre-checks (HEAD on `origin/main`, tag free unless `--force-retag`, ghcr login, clean tree unless `--allow-dirty`), requires each selected local image to exist with an `org.opencontainers.image.revision` label equal to HEAD, and refuses before pushing anything otherwise; it cannot be combined with `--no-push` or `--allow-unpushed`. `images.yml` stays for `v*` tags and the platform images, run by hand; its dev jobs remain as a manual fallback (`variant=dev`) but fail when `<sha12>-dev` already exists unless the `force_retag` input is true, so a CI run cannot retag a locally published image. After a push, pin the printed `...:<sha12>-dev@sha256:<digest>` references in chelabase as the Compose defaults of `NEON_IMAGE` (storage) and `COMPUTE_NODE_IMAGE` (compute), then run chelabase's e2e against them.
