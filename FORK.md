# Chelabase Fork of Neon

This is Chelabase's hard fork of [neondatabase/neon](https://github.com/neondatabase/neon), based on upstream commit fa504217 (2026-08-31, main HEAD when upstream froze). PostgreSQL sources are pulled from [chelabase/postgres](https://github.com/chelabase/postgres) branches `REL_14_STABLE_chelabase` through `REL_17_STABLE_chelabase`.

## Policy

This is a hard fork: all of the code, the core engine included (pageserver, safekeepers, the PostgreSQL patches), is ours to change, and we change it whenever that is the right fix. Where code came from, how invasive a change is, or how far it moves us from the original base is never a reason to leave a bug or document a gap instead of fixing it. Performance changes need supporting profiling evidence.

## Pageserver changes

The changes we made to the pageserver, each fixing a bug Chelabase hit.

- **Detach waits for its ancestors' WAL.** Before copying anything, `detach_ancestor` waits for every ancestor level to ingest its WAL up to the cut (an ancestor reloaded since its last flush only has its WAL up to its disk consistent LSN until its walreceiver catches up). Each wait is up to 30 s, one level after the other, so the worst case is 30 s × the chain's depth; a timeout returns 503 ("not caught up yet, retry later"), a broken ancestor 500.
- **Multi-level detach copies every ancestor's layers.** Under `DetachBehavior::MultiLevelAndNoReparent` the detached timeline gets each level's layers up to that level's cut (straddling deltas rewritten, the rest copied by reference). Before copying, it waits for every level's queued uploads to finish, so a layer copied by reference is already in remote storage (a stopped upload queue answers 503, shutting down). This holds because every layer-map update (flush, compaction and its image layers, gc-compaction, import) schedules its uploads under the same layer-map write lock that makes the new layers visible. Like the HTTP handler's own drain, the wait has no timeout: a stuck upload queue holds the detach until shutdown. Nothing is reparented.
- **Multixact next offset, as Postgres writes it.** A multixact `CREATE_ID` also sets the next multixact's offset (when still zero), as Postgres' `RecordNewMultiXact` does, through one combined record `NeonWalRecord::MultixactOffsetCreateWithNext` at **enum index 8** (just before the testing-only `Test` variant; byte tests pin the indices). `MultixactOffsetCreate` stays decodable but is no longer emitted. This is a stored format: **never roll the pageserver back to a build without the variant** once it has ingested a `CREATE_ID`: its layers then hold discriminator 8, and an older pageserver can't read those pages.
- **Missing multixact offsets pages.** When the next multixact's entry is on the next offsets page (once per 2048 multixacts), ingest checks that the page exists and, if not (WAL from older minors), writes it as one image with the entry set. Mid's own page is never checked: two reads per `CREATE_ID` made multixact ingest about 20× slower. A `CREATE_ID` on an offsets page the pageserver never received (WAL from a compute older than Postgres' 2025-12-03 multixact back-patch, e.g. a physical import from an older minor) fails with "no base image"; Chelabase doesn't run such computes. Revisit before adding physical imports or running computes we didn't build.
- **Reads at retained LSNs below the GC cutoff.** An LSN below a timeline's applied GC cutoff is still served when GC keeps it whole: a child's branch point (`retain_lsns`) or a lease. The match is exact: the LSN equals the kept point, or normalizes (`normalize_lsn`) to the same LSN and lies at or after it. Never below it and no ranges: gc-compaction keeps only the image at the exact point and drops the history below. The same rule applies at every scope check: basebackup (libpq and gRPC), get_page and the other page requests, and branch creation. A branch created there gets its GC cutoff capped at its own branch point, so its computes can read from the start.
- **Leases at kept points.** Every lease is keyed at the exact requested LSN, never normalized (a normalized key let a static compute at a WAL page start lose its point once the cutoff passed it). A read matches a lease when its LSN is equal to the kept point, or the same point past the page header. A lease below the GC cutoff is granted only when the requested LSN is equal to a kept point, or the same point past the page header, checked and inserted under one `gc_info` write lock. Branch creation at a kept point below the cutoff takes a short lease there under that same lock, so a child dropped meanwhile can't let GC (legacy `gc_timeline` or gc-compaction) drop the point before the new branch registers its own. A static compute at a kept point therefore keeps its data through compute_ctl's lease renewal even if the child is deleted. Accepted risk: a reader holding no lease (its lease request failed or was never made) loses the point when the last child that kept it is deleted. On a root timeline its reads then fail; on a branch's parent a page whose history is gone falls through to the grandparent and returns stale data silently (legacy GC works from a snapshot of the retain points taken before the new cutoff is applied). Reads at a point kept by an offloaded child may hit cold layers (performance only).
- **Replication slot states in the basebackup.** Every `pg_replslot/<slot>/state` aux file is checked as the compute's `RestoreSlotFromDisk` checks it, in its order (at least the 16-byte header, `SLOT_MAGIC`, the major's `SLOT_VERSION`: 2 on v14/v15, 3 on v16, 5 on v17, a `length` of 184 with the entry exactly 16 + 184 bytes, the CRC-32C); a malformed one, which would make every start PANIC, is skipped with a warning ("skipping malformed replication slot state <path>") and never counts towards `restart.lsn`. Only a persistent slot's well-formed state counts towards `restart.lsn`; a replica's basebackup ships no slot.

## Postgres changes

The changes we made to the PostgreSQL fork (chelabase/postgres, v17 only for now; they ship on `REL_17_STABLE_chelabase`, which `vendor/postgres-v17` and `vendor/revisions.json` pin).

- **Temporary replication slots never reach the pageserver (U16).** Only a persistent logical slot's state is logged as a `neon-file:` aux file (`SaveSlotToPath`, and the delete in `ReplicationSlotDropPtr`); a temporary or ephemeral slot never gets one. A stale copy left by an older compute (which copied every logical slot) is cleaned at start: on a primary started from a basebackup, the names of the non-persistent slots `RestoreSlotFromDisk` deleted are remembered and `LogDiscardedSlotFiles` writes one empty `neon-file:` message per name once WAL can be written (idempotent: a stop before the safekeepers have them repeats it at the next start). A basebackup start is told apart by the control file before recovery: `DB_SHUTDOWNED` with checkpoint location 0, which only the pageserver writes (`neon.signal` can't tell, it is never removed). A restart of the compute's own data directory, after a crash (`DB_IN_PRODUCTION` or a recovery state) or after a clean shutdown (whose checkpoint has a real location; a walsender killed after it can leave a temporary slot behind), finds only its own local non-persistent slots, never copied, and nothing is recorded for them.
- **`chelabase_keys` stream callbacks (W9).** The output plugin implements `stream_start`, `stream_stop`, `stream_abort`, `stream_commit`, `stream_change` and `stream_truncate`, with per-transaction state under the decoding context, so a big transaction streams while it runs instead of spilling to disk past `logical_decoding_work_mem`. Regress `stream` and `stream_edges`, and isolation `stream_interleave` and `stream_many`, cover it.

## Compute extension changes

- **DDL forwarding sends LOGIN, VALID UNTIL and "touched" roles.** `pgxn/neon/neon_ddl_handler.c` adds optional keys to each forwarded role `set` entry: `"login": true|false` (the catalog's value at commit; always sent for a role created in the transaction, otherwise when LOGIN or NOLOGIN was given), `"valid_until": "<text as written>"`, and `"touched": true` when another attribute (CREATEDB, CREATEROLE, INHERIT, REPLICATION, BYPASSRLS, SUPERUSER, CONNECTION LIMIT) or a membership changed: GRANT/REVOKE of a role marks every grantee and granted role, CREATE ROLE ... IN ROLE/ROLE/ADMIN and ALTER GROUP the named role. A touched-only entry is `{"op":"set","name":…,"touched":true}`. A role without a password is sent with an explicit `"password": null` when it was created in the transaction, renamed, or carries any of these keys; attribute-only entries carry no password key; password-only bodies are unchanged (`ALTER ROLE a PASSWORD NULL` alone is still `{"op":"set","name":"a"}`). Savepoints: what a released one gave wins, `touched` is OR-ed, and an entry that gave no PASSWORD clause keeps the parent's password. A rolled-back one counts for nothing, at any depth: a savepoint released into an enclosing one that is then rolled back is dropped with it (its options merge into a table made at the enclosing level, which the rollback drops, and their strings live in memory freed only with that level). compute_ctl's own changes (`apply_config` and the migrations) run with `neon.forward_ddl` off: they are never forwarded, and a compute's start never depends on the console being reachable.
- **DDL forwarding tracks roles and databases by OID, never by name.** Keyed by name, with renames chained through `old_name`, a transaction that dropped a role, renamed another onto its name, created a third under it or renamed that one away mixed the roles' state: DROPs were lost, a role created in the transaction claimed an `old_name` (the receiver then moved the old role's row and data keys to it), a dropped role's attributes went out for another role, the payload depended on hash order (database renames and swaps in savepoints too), and some valid transactions failed in the handler itself ("Failed to get encrypted password": a password set before a rename-then-drop was looked up under the dropped name). Now each role a statement touches is recorded by OID with its name before the transaction (the name at its first touch; any rename is a touch) or as created in the transaction (recorded after CREATE ROLE runs, when the OID exists); the options only the statements know (the password as typed, which options were given) are kept per savepoint by OID. At commit the catalog, looked up by OID, says which roles exist and under which names, so savepoint rollbacks need no undo. The payload then follows:
  - a role created in the transaction that exists at commit: a `set` under its name, never with `old_name`, with its password (or an explicit null) and its login;
  - a role from before the transaction that exists at commit: a `set` with `old_name` (its name before the transaction) when renamed, plus whatever its statements changed;
  - a role from before the transaction that is gone: `{"op":"del","name":<its name before the transaction>}`, unless a role now holds that name (a new role, sent with `recreated`, or a rename onto it, which the receiver refuses or replaces when it moves its rows). A role renamed and then dropped is a `del` under its old name, without `old_name`.
  - **Recreated:** a role created in the transaction under a name that held a role, from before the transaction, that is gone (dropped under any name) carries `"recreated": true`, always with `"touched": true` (the old role's members lost their membership). The key is a boolean, sent only when true and only on `set` entries. A name freed only by a rename isn't marked. The receiver runs its DROP-time live data-key check for a recreated entry, so `DROP ROLE app; CREATE USER app [PASSWORD 'x']` can't pass the old role's data keys to the new one. A rename onto a gone role's name is `touched` too.
  - The receiver applies renames, then sets, then dels.
  - **Databases** work the same way: each database a statement touches (CREATE after it runs, ALTER ... RENAME, ALTER ... OWNER, DROP) is recorded by OID with its name before the transaction; at commit a created one is a `set` with its owner, one from before the transaction a `set` with `old_name` when renamed and `owner` (the catalog's) when its owner changed, and a gone one a `del` under its name before the transaction. The receiver keeps a database's owner by name, so every database owned by a role renamed in the transaction is sent again with its owner.
- **PREPARE TRANSACTION is refused while a transaction has role or database changes to forward** ("cannot PREPARE a transaction that changed roles or databases"): the prepared transaction would commit later, maybe in another session, where nothing forwards its changes. Without changes (or with `neon.forward_ddl` off) PREPARE works as before.
- **The DDL forwarding model test.** `test_runner/regress/test_ddl_forwarding_model.py` runs every sequence of role operations (CREATE USER ... PASSWORD, CREATE ROLE, DROP, RENAME, ALTER ... PASSWORD / PASSWORD NULL / NOLOGIN), database renames and savepoints (SAVEPOINT, RELEASE, ROLLBACK TO, nested three deep) up to 5 statements, over three role names (two exist, one backing a live data key) and three database names (two exist, one owned by a role), in five configurations: roles with a short alphabet (38,453 sequences), all role operations (398,382), roles with database renames (111,257, about a third of them rejected by Postgres because the owner of a database can't be dropped), the branch owner and a reserved name (30,313), and the role cap (30,313). Each payload is applied to a model of the receiver (`ddl.rs` `steps()`, `decide()`, `apply()`, `finish_role_moves()`, `finish_db_moves()`, with its owner, reserved-name, live-key and role-cap refusals), and the result must match the catalog after the commit: refusals exactly when the commit broke one of the receiver's rules; copies (verifier and login flag) for exactly the roles with a password; every live data key under its own role's current name; every forwarded plain password the one its verifier was made from; the databases with their owners' current names; `recreated` exactly where a new role took a gone role's name; and a resync asked for when a role from before the transaction was dropped. Two receiver gaps it found are checked against a model with the receiver fixed (and logged against the current one): a branch owner dropped and created again is accepted, and the role cap is checked before the delta's dels (DROP a; CREATE USER c at the cap is refused). It runs in 40 shards, in parallel, and isn't rerun on failure.

- **Protected databases.** A database listed in `neon.protected_databases` (the branch's main database) can't be dropped or renamed by a non-superuser, and no other database can be renamed to a protected name (a rename then drop would get around the refusal); superusers can do both.
- **Managed member roles.** `cb_m_*` (any case) and `chelabase_realtime` are Chelabase's: a non-superuser can't create, alter, rename, drop, grant, revoke or change the membership of one (CREATE ROLE ... IN ROLE/IN GROUP/ROLE/ADMIN, ALTER GROUP ... ADD/DROP USER, GRANT/REVOKE, ALTER ROLE ... IN DATABASE, a member's own included). The refusal comes before anything is recorded for forwarding, so a refused statement forwards nothing.
- **Born closed on a protected branch.** A branch is protected when `neon.branch_protected` is on (`PGC_SIGHUP`: compute_ctl writes it from the spec, and no session, database or role setting can change it) or when the session's database carries the schema guard (the event trigger `chelabase_schema_guard_ddl`, `ENABLE ALWAYS`, owned by a superuser and running a function a superuser owns). While protected, whichever database the session is in: a non-superuser's CREATE DATABASE runs with `ALLOW_CONNECTIONS false` and gets the marker `neon.born_closed = on` (a database setting, `PGC_SUSET`, so its owner can neither set nor reset it), and ALLOW_CONNECTIONS (any value) or IS_TEMPLATE true in it is refused; ALTER DATABASE ... ALLOW_CONNECTIONS/IS_TEMPLATE is refused, as it is on a marked database from anywhere. The member-roles reconcile guards a born-closed database, opens it and resets the marker. CONNECTION LIMIT stays the owner's, a missing database gets Postgres' own "does not exist", superusers are untouched, and an unprotected branch behaves as Postgres does.
- **REASSIGN OWNED in DDL forwarding.** REASSIGN OWNED changes database owners without an ALTER DATABASE ... OWNER, so every database the listed roles own is forwarded with its owner as it is at commit. A non-superuser can't REASSIGN OWNED ... TO the privileged role (CREATE/ALTER DATABASE ... OWNER refuse it too); a superuser can (compute_ctl drops roles that way as `cloud_admin`).
- **compute_ctl: member logins.** The spec's `member_logins` (`allowed_cidrs`, `client_cns`) becomes a block at the top of `pg_hba.conf`, between marker lines: one `hostssl ... scram-sha-256 clientcert=verify-full map=chelabase_member` line per allowed CIDR (`all` for an empty list), then `reject` lines for every other member login (TCP, replication, Unix socket). No `member_logins`, no TLS, a major below 17 (which refuses `map=` with a client certificate check) or an unreadable `PG_VERSION`: only the `reject` lines. `pg_ident.conf` gets the `chelabase_member` map lines, one per CN, between their own markers. Start and reconfigure (followed by a reload) both replace the text between the markers and keep the rest of each file byte for byte; a block cut short (one marker without the other, a marker twice, out of order) is an error naming the file, which is left as it was.
- **compute_ctl: TLS.** With the `tls_experimental` feature (and only then: Postgres' config, pgbouncer, local_proxy and the certificate watcher all go through one check), `ssl_ca_file` is set whenever the TLS config has `ca_path`. The watcher polls the key, certificate and CA file every 60 s (one length-delimited digest of the three); on a change to any of them it copies the key and certificate into pgdata and reloads Postgres, never touching the compute's status. The copy happens only when the key matches the certificate and (with `ca_path`) the certificate is valid now and chains to the CA file (P-256 ECDSA), so a renewal or CA rotation seen half-written loads nothing; a failed (or panicking) reload stays pending and is retried at every poll, even if the files don't change again; the watcher stops only when the compute terminates. The checks use aws-lc-rs. A reconfigure writes postgresql.conf, pg_hba.conf and pg_ident.conf all-or-nothing: every new content is computed and checked first, and on any failure none of them changes. Copies are serialised and use unique temporary files, and a failing `pg_ctl reload` is an error, not a panic.
- **compute_ctl: branch protection.** The spec's `branch_protected` (default false) is written into `postgresql.conf` as `neon.branch_protected` at start and on reconfigure (then reloaded), after the spec's own `postgresql_conf` and `settings`, so neither can override it.
- **compute_ctl: migrations before `running`.** Migrations run before the compute reports `running`, on a connection started with `neon.forward_ddl=off`, `lock_timeout=5s` and `statement_timeout=2min`. A failure that leaves a fail-open migration (one that removes a privilege) unapplied fails the start; any other failure is logged and counted, and the next start retries.
- **compute_ctl: the internal API on loopback behind a secret.** The internal server (port 3081 by default; the neon extension's extension downloads, local_proxy, `/grants`, `/extensions`, `/refresh_configuration`) listens on loopback only, `127.0.0.1` and `::1` (a missing `::1` is tolerated only on `EADDRNOTAVAIL`/`EAFNOSUPPORT`; every listener is bound before the start goes on, and a bind error fails the start). Every route needs `Authorization: Bearer <secret>`: a per-start secret (32 bytes from the OS RNG, hex) that compute_ctl writes to its token file (`--internal-api-token-file`, default `compute_ctl_internal.token` beside pgdata), compared in constant time; anything else is 401 with `WWW-Authenticate`, nothing bypasses it, and the secret is never logged.
- **compute_ctl: the external API always authenticates.** Every external route, `/metrics` and `/autoscaling_metrics` included, needs a JWT signed by a key of the compute's JWKS: a missing, malformed or non-Bearer header, a bad signature or an expired token is 401 with `WWW-Authenticate: Bearer`, and the `INSTANCE_ID` bypass is gone (an `INSTANCE_ID` changes nothing). A token with the `metrics` scope opens only `GET`/`HEAD` on `/metrics` and `/autoscaling_metrics`, whatever `compute_id` it carries, and is 403 everywhere else.
- **compute_ctl: storage token refresh.** `POST /storage_token` (external API, `{"token": "<storage token>"}`) writes a new tenant storage token to the storage token file (`--storage-auth-token-file`, default `storage_auth.token` beside pgdata) and holds it, changing neither the status nor any config: 204 written; 400 a bad body, an invalid token or a compute started without storage auth; 412 outside `running` and `configuration_pending`; 500 the file couldn't be written (the old one is kept). The storage token file is written before the safekeeper sync and Postgres start, and first in every reconfigure.
- **compute_ctl: the `storage_token_refresh` capability.** compute_ctl names its capabilities in the `Compute-Capabilities` header of its spec fetch (always `storage_token_refresh`) and in `/status` (`storage_token_refresh` only while the compute holds a storage token), so the control plane gives expiring storage tokens only to a compute that can refresh them.
- **compute_ctl: `/grants` and `/extensions` narrowed (RT4-6).** The internal secret is `cloud_admin`-grade, so `/grants` grants only `USAGE`/`CREATE` on a schema a non-superuser owns to an existing ordinary, unmarked role, and `/extensions` installs or updates only trusted extension versions: every version whose script `CREATE EXTENSION ... VERSION` or `ALTER EXTENSION ... UPDATE` runs (the install script and the update path) must have a trusted control file. A refusal is 403 and runs nothing.
- **compute_ctl: storage auth can't change while running (RT4-7).** On a running compute, a `/configure` without `storage_auth_token` when the compute has one (or with one when it started without) is refused with 400 before anything changes; a storage token only arrives through `POST /storage_token`, and turning storage auth on or off needs a restart. `/promote` and the configuration refresh can't change it either, nor carry an invalid token.
- **compute_ctl: DuckDB pinned.** `postgresql.conf` ends, after the spec's settings, with `duckdb.disabled_filesystems='LocalFileSystem'`, `duckdb.autoinstall_known_extensions=off` and `duckdb.autoload_known_extensions=off` (all `PGC_SUSET`), so pg_duckdb (in the `extensions-all` image) never reads local files or installs and loads its own extensions, whatever the spec says.
- **compute_ctl: realtime logins.** The spec's `realtime_logins` (`allowed_cidrs`, `client_cns`) becomes a marked `pg_hba` block right after the member block: one `hostssl all chelabase_realtime <cidr> scram-sha-256 clientcert=verify-full map=chelabase_realtime` line per CIDR (`all` for an empty list), then `reject` lines for every other `chelabase_realtime` login; without `realtime_logins`, TLS or v17, only the `reject` lines. `pg_ident.conf` gets the `chelabase_realtime` map between its own markers, right after the member map. A realtime block moved by hand is moved back after the member block. `pg_ident.conf` is written before `pg_hba.conf` and put back when `pg_hba.conf` can't be written, so new hba lines never map through an old ident map.

- **Token files.** compute_ctl writes the tenant storage token and the secret of its internal server each to its own file outside pgdata (`<token>\n`, mode 0600, replaced by rename) and names them in `postgresql.conf` as `neon.storage_auth_token_file` and `neon.compute_ctl_token_file` (both `PGC_POSTMASTER`, so a session can't point the reader elsewhere). `pgxn/neon/token_file.c` reads them at every pageserver and safekeeper connect and every call to compute_ctl's internal server: one `stat()` per call, a per-process cache keyed on the open descriptor's device, inode, size, mtime and ctime, and fail closed (a missing, unreadable, empty, oversized or invalid file gives no token and drops the cached one; one WARNING per state change, never the content). A path that isn't a regular file (a FIFO, a directory) is refused from the `stat()` and never opened. A failure stays cached under the file's identity only when it is the file's own (not a regular file, a permission error, bad content); a transient open or read error (EMFILE, ENFILE, ENOMEM, EIO) is retried at the next call. `NEON_AUTH_TOKEN` is gone from the compute's environment (compute_ctl, Postgres and `--sync-safekeepers`).
- **Extension download names are escaped.** The neon extension asks compute_ctl's internal server for `/extension_server/<name>` with the name percent-encoded (`curl_easy_escape`): a `CREATE EXTENSION` or library name holding `?`, `#`, `%`, `&` or `/` stays that one name and never becomes a query string (`?is_library=true`), a fragment or another path.
- **Personal-login marker guard.** `chelabase.managed_role` is a role-wide setting (`PGC_SUSET`, no runtime effect) that a superuser sets on a personal login; `neon_ddl_handler.c` then treats the role as managed like `cb_m_*`, and refuses every non-superuser change of the marker itself (even with a SET privilege granted by mistake). `COMMENT ON ROLE` and `SECURITY LABEL ON ROLE` on a marked or managed (`cb_m_*`, `chelabase_realtime`) role are refused to non-superusers too (42501, the guard's usual message): Postgres lets a CREATEROLE role (with ADMIN OPTION on PG16+) do both, and a label is a provider's policy input (with `anon`, masking). The guard's two statement lists (the cheap early return, then the checks after `superuser()`) name the same statements, and the second ends in `Assert(false)`.
- **`neon.allow_unstable_extensions` is `PGC_SUSET`.** A non-superuser can no longer enable the unstable extensions (`neon.unstable_extensions`) for a session.
- **Stream callbacks.** The `chelabase_keys` stream callbacks (see Postgres changes) let the realtime slot stream a big transaction instead of spilling it.

## Storage auth changes

The pageserver, the safekeepers and the storage controller.

- **The `metrics` scope.** `Scope::Metrics` (`"metrics"`) is a read-only scope: a `metrics` token is refused (403) on every path but exactly `/metrics`, before routing, so no other handler sees it. `/metrics` and `/profile/{cpu,heap}` need a token when auth is on (the status, health and docs routes stay public): the pageserver's and safekeeper's `/metrics` take `metrics`, `admin` or their own global scope, the storage controller's `metrics` or `admin`; the profiles take `admin` or the own global scope (the storage controller: `admin`).
- **Every route authorized before its handler.** Every pageserver and safekeeper API route authorizes the request for its route before its handler reads the body or the query: the path's tenant, or with none the server's own global scope. The control-plane routes (shard split, location config, secondary upload, download and status, `wait_lsn`, remote-storage scan, tenant delete, `/v1/tenant/config`, the testing tenant break; the safekeeper's `POST /v1/tenant/timeline`) take the global scope only, whatever tenant they name: no tenant token passes there, not even for its own tenant. The storage controller refuses before routing the scopes none of its routes takes.
- **`check_permission` is total.** A tenant token without `tenant_id` is refused ("tenant scope without a tenant id", 403) instead of panicking, in the HTTP and libpq checks and the pageserver's gRPC interceptor; a libpq check without claims is Unauthorized, not a panic.
- **`nbf` is validated.** A token isn't valid before its `nbf` nor after its `exp` (60 s leeway), and a token whose `exp` or `nbf` is present but not an integer NumericDate is refused (it used to skip the check and never expire).

## Proxy changes

- **The Valkey password from a file.** `--redis-plain-password-file` holds the password of `--redis-plain` (whose URL must then carry none; `redis://` or `rediss://` only), so it is off the command line; it is an error without `--redis-auth-type plain`, and a password with control characters is refused.
- **local_proxy's compute_ctl token file.** local_proxy reads the bearer secret of compute_ctl's internal API from `--compute-ctl-token-file` (default `/var/db/postgres/compute_ctl_internal.token`) before every call, never cached (compute_ctl draws a new one at each start): opened non-blocking, only a regular file is read, and an invalid file means no `Authorization` header and a rate-limited WARN. The proxy binary takes the same flag for its testing `local` backend.
- **The control-plane token from a file.** `--control-plane-token-file` holds the JWT the proxy sends to the control plane (one line, read once at startup), so `NEON_PROXY_TO_CONTROLPLANE_TOKEN` and `--control-plane-token` are off the environment and the command line; giving both ways is an error, and so is the file with an auth backend that never calls the control plane.

## Storage controller changes

- **Backoff on serialization failures.** A database call of the storage controller (storcon) that fails with a serialization failure is retried at most 20 times with full-jitter exponential backoff (10 ms doubling to 500 ms), its connection returned to the pool before each sleep; the retries of each call are observed in the histogram `storage_controller_database_query_retries`.

## Compute image

`compute/compute-node.Dockerfile` builds the compute with one of three extension sets (`EXTENSIONS=none|minimal|all`). The published dev image (`publish-dev.sh`) is `EXTENSIONS=minimal`, the extensions Chelabase runs today. The Dockerfile's default, `EXTENSIONS=all` (the `extensions-all` stage, with its `extension-tests` image), keeps the full extension set; `docker-compose/chelabase-ext-test.sh` builds and tests it, and it isn't published yet.

- **Removed:** pgjwt, pgrag (with onnxruntime and its patch), pg_tiktoken, pg_mooncake, and the v14-v16 pgx_ulid 0.1.5 (their `docker-compose/ext-src` tests go with them).
- **Bumped (minimal):** timescaledb 2.31.0, pg_partman 5.5.0, pg_cron 1.6.8.

## PostgreSQL Minors

When a new PostgreSQL minor release becomes available:

1. Merge the `postgres/postgres REL_x_y` tag into `REL_x_STABLE_chelabase` in chelabase/postgres (pull request, run `make check`).
2. Bump the submodule commit here and update `vendor/revisions.json` (pull request). The gate is `.github/scripts/ci-local.sh` (lint, build, Rust tests) on the bump, plus a local `make check` for that major in chelabase/postgres.
3. Publish dev images with `.github/scripts/publish-dev.sh` and run chelabase's e2e against them.
4. Process oldest minors first.

Neon's own `REL_x_STABLE_neon` branches remain read-only references; we do not track them.

## Tests

CI quarantines known test failures in `test_runner/known_failures.txt`, each with a reason. This list may only shrink.

## Checks

The gate for every PR is `.github/scripts/ci-local.sh`: lint (self-tests, actionlint, fmt, clippy, cargo deny, ruff, mypy), build, and the Rust tests. It runs on a developer machine inside the same `ghcr.io/chelabase/neon-build-tools` image as `.github/workflows/pr.yml` (pulling the image needs no login: the GHCR packages are public), with caches in the Docker volumes `chela-neon-cargo`, `chela-neon-target` and `chela-neon-sccache` and logs under `.ci-local/` (git-ignored). Use `--pg v14|v15|v16` for the older majors.

The `chela-neon-sccache` volume (mounted at `/sccache-cache`) is shared by every clone whatever the suffix: sccache wraps rustc, so a task clone reuses the compiled crates of the others. The script downloads a pinned static sccache once into `${XDG_CACHE_HOME:-$HOME/.cache}/chela-neon/`, re-checks its sha256 on every run (a damaged copy is reinstalled) and mounts it read-only at `/opt/sccache`. Only release builds benefit, since sccache skips incremental crates. The build and rust-tests steps print `sccache --show-stats`.

GitHub CI is manual-only, as standing policy: `pr.yml` is `workflow_dispatch` only, and branch protection on `main` requires a PR but no status check. `images.yml` runs only for `v*` tags and the platform images, by hand.

Neon's pytest regression suite is opt-in and required for no PR: `ci-local.sh --regress [-k <expr>] [-n <workers>]` runs it for a targeted check, for example to debug one test. When an image changes, chelabase's own e2e covers the parts we use. The regression run deselects `test_runner/known_failures.txt` (fails on GitHub's runners too) and `test_runner/known_failures.local.txt` (fails only in the local run); both use the `<nodeid>  # <reason>` format and may only shrink.

Quick mode, for patch work: `ci-local.sh --only build,rust-tests,pg-check,regress` runs just the listed steps (in pipeline order, lint skipped; the last `--only` decides, and `regress` in it implies `--regress`), and `--test-filter <nextest expr>` (needs `rust-tests` in `--only`) narrows `cargo nextest run` with `-E`, ANDed with the quarantine filter (no newlines; a filtered run skips `cargo test --doc`, which `-E` can't narrow). The `pg-check` step (selectable only through `--only`, ordered after `rust-tests` and before `regress`) builds Postgres for `--pg` if needed and runs `make check` in `build/<pg>` and, for v17, in `build/v17/contrib/chelabase_keys`; any failure fails the step, and each `regression.diffs` is printed into the step's log. `CHELA_NEON_VOLUME_SUFFIX=<suffix>` (`^[a-z0-9-]+$`) switches to the volumes `chela-neon-cargo-<suffix>` and `chela-neon-target-<suffix>`, so parallel clones keep separate build state and stamps.

## Publishing dev images

The Postgres 17 dev images are built on a developer machine and pushed from there (the GitHub job took 111 minutes): `.github/scripts/publish-dev.sh [--no-push] [--only storage|compute]` builds `ghcr.io/chelabase/neon-storage:<sha12>-dev` and `ghcr.io/chelabase/neon-compute-v17:<sha12>-dev` from the checked-out commit (`<sha12>` = chelabase's `neon_tag`), runs `image_variant_test.sh` on the storage image, and only then pushes. It needs a clean tree at a commit on `origin/main`, initialised submodules, and `docker login ghcr.io` for the push (the packages are public: pulling needs no login, pushing does), and it refuses to overwrite an existing tag without `--force-retag`. The images carry no SBOM or provenance attestations. To build once and push later, build with `--no-push --allow-unpushed` from the round branch and test those images; once `main` is fast-forwarded to that SHA, `publish-dev.sh --push-only` pushes the exact local images without rebuilding or re-running the variant test. It keeps the push pre-checks (HEAD on `origin/main`, tag free unless `--force-retag`, ghcr login, clean tree unless `--allow-dirty`), requires each selected local image to exist with an `org.opencontainers.image.revision` label equal to HEAD, and refuses before pushing anything otherwise; it cannot be combined with `--no-push` or `--allow-unpushed`. `images.yml` stays for `v*` tags and the platform images, run by hand; its dev jobs remain as a manual fallback (`variant=dev`) but fail when `<sha12>-dev` already exists unless the `force_retag` input is true, so a CI run cannot retag a locally published image. After a push, pin the printed `...:<sha12>-dev@sha256:<digest>` references in chelabase as the Compose defaults of `NEON_IMAGE` (storage) and `COMPUTE_NODE_IMAGE` (compute), then run chelabase's e2e against them.
